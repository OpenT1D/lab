## Exact candidate host plan

`native_host_plan.prepare` derives the unchanged provisional native profile for
the fixed candidate in `native_preflight`, with a separately located staging,
packet, output and evidence root. It binds explicit native worker/reader/control
sources and all authority files, exact profile bytes/hash, fixed argv and passed
environment, DEVNULL stdin and closed inherited descriptors. It accepts no runtime
substitution, profile text, native-case outcomes or admission registry.

This is a static plan. The function reads repository controls and hashes trusted
Python identity, never supplied private roots or the selected runtime. The trusted
source reader requires POSIX; unsupported systems refuse before source intake.
Supplied private root strings are checked lexically; their existence,
device/inode/UID, ACLs, physical aliases and
restore scope still require separate qualification. The plan itself is private
when real paths or interpreter identity are included; saving it needs accounting.

Every native-family slot has `state: not_run` and `origin: none`. C15–C18 remain
unrun. The native launcher/worker do not yet wire the tooling fixture's FD3/4
handoff; the planner makes that gap explicit and changes neither component.
It adds no execution route, setup receipt or successful native observation.
The old tooling profile/result is not substituted for this candidate's profile.

The existing profile retains broad system-library read/map, global metadata and
mach-lookup rules. Static source hashes do not establish the dynamic bootstrap,
computed TypeScript imports, addon behavior, IPC isolation or atomic expected-byte
exec. Actual parent/child allow/deny twins, process ownership and stops, module/
addon/phase observations and reconstruction need their own admitted qualification.
The [qualification packet](ot062-lt1-qualification-packet.md) retains the scientific
C15–C18 criteria; no baseline, tolerance, time convention or native oracle changes.

Rights and runtime-risk decisions remain separate. On 4 November 2026 the
[Node 26 inquiry](https://github.com/nodejs/nodejs-dependency-vuln-assessments/issues/467)
and [Node 24 inquiry](https://github.com/nodejs/nodejs-dependency-vuln-assessments/issues/492)
were still open with no responses. Those two inquiries supply no finding for the
selected Node 22 candidate; this is not a claim about all possible upstream
guidance. The [existing disposition](ot062-lt1-private-controls.md) remains deferred
pending exact-packet rights/security decisions or a separately reviewed successor.
No verifier, exploit, package install or candidate runtime is run here.

## Whole published-packet cleanup request

`packet_cleanup` prepares a data-only removal request for an exact published
reconciliation packet. External pins identify its manifest, original registration,
historical context and producer. Current helper source and current removal context
have their own independent bindings. Exact flat members, typed intent, parent and
physical root are verified before returning a request for the whole namespace.

Cleanup preparation does not call full reconciliation replay or inspect original
live paths. An old missing root/journal or a producer upgrade cannot itself force
continued retention of the packet. This validates the target inventory, not the
truth or continued validity of its stored evidence. Original reconciliation is
explicitly not reassessed; no absence observation or approved state is invented.

When externally reviewed packet-copy accounting and provenance are supplied,
they must match the separate accounting branch and target identities exactly.
They cannot be replaced by the stored unapproved absence proposal. Without usable
accounting, the request remains visibly blocked by unregistered packet copies.
That distinction also covers pre-correction published packets whose accounting
could not fit: the target can be inventoried without claiming complete accounting.

The current assessment preserves inherited origins, unknown clocks, holds,
predecessor history and recovery limits. Historical packet context is not relabeled
as current removal context. The request/report remains unsaved and unadmitted;
saving it creates further private records requiring accounting. Pending and partial
publication prefixes require the separately reviewed manual exact-inventory route.

Tests use only fresh invented metadata and the unchanged process owner. They
exercise complete and interrupted exact packet removal through a fixture-only
reviewed injection; the production removal entry still refuses under its empty
authority. They do not access or remove an existing private pilot, backup,
snapshot, container or key, and do not establish effective private erasure.

## Remaining operational decisions

Before selected-runtime setup, complete the exact rights/security and harness/
reader decisions and reviewed storage/copy/restore scope. Actual setup needs its
own admission and verified receipt. Bounded native qualification then needs a
separate execution decision; already passing the same native cases is not inferred
from a plan and is not substituted for that decision.

Before private removal, resolve original clocks, holds and complete live/
quarantine/snapshot/backup coverage, review an exact operation and admit only that
request. Path absence alone proves neither timely removal nor ordinary restore
exclusion or physical erasure. All four production authority lists stay empty.
