# Shared M3 integration evidence

Date: 1 November 2026. Scope: bounded internal software integration from merged
PR #45 (`5dbdd24703480c7504fce3db6e6867ff33b3ca3e`), under
[decision 0091](../decisions/0091-m3-shared-workbench.md). The
[installed guide](../installed-m3.md) owns user commands. Root tooling, M3
estimator execution, installed workers, browsers and hosted CI are separate
sources of evidence. No synthetic result establishes human predictive accuracy,
biological validity or independent intended-user acceptance.

## Reuse and preserved contracts

The adapter calls the existing M3 coordinator and authoritative parent/child
readers. No file under `experiments/m3/`, historical protocol, frozen baseline or
tolerance is changed. Predictor bundles, all planned people/origins, causal
availability, elapsed microseconds, mg/dL, persistence and complete common
support retain the native semantics. The installed context binds only current
application revision/dirty metadata and the fixed supervised child entry.
Archived source and runtime selectors remain evidence, never executable reader
selection. Native child archives retain their original strict inventories.

The new domain adapter owns resource capture, explicit location rebasing and
binding native results to the frozen bytes. Existing ledger, lease, retry,
recovery, process supervisor, GUI concepts and verified report downloads are
reused. The thin GUI adds a task selector, context and raw comparison editor;
there is no second forecasting implementation or training pipeline. A freeze
can compare exact inspected input hashes before publishing the ledger event,
closing the validation-to-capture change window for referenced local files.

## Selected checks and retained failures

`test_m3_services.py` covers passive source intake, hash/feature refusal,
missing and invalid observations, retained long failed prefixes, all planned
slots/origins, resealed report refusal, unknown readers, changed referenced bytes
and unfinished recovery. `test_installed_m3.py` builds an actual noneditable
wheel and exercises Python/CLI identity, direct/installed trace and common-metric
parity, retry/derivation, physical input/predictor removal and relocated reports.
Its actual slow predictor is cancelled; owned cleanup completes and an unrelated
process survives. Missing input and nonfinite output retain native incomplete
reports and require explicit incomplete-evidence reading.

The existing M3 contract families exercise original intake, causal windows,
coverage/metric arithmetic and historical readers. Descriptor tests retain the
exact 1–5 rosters and reject descriptor-6 task/policy promotion. The new actual
Chromium test covers concept correction, referenced-byte invalidation, freezing,
execution after deleting original inputs/predictors, exact report downloads,
relaunch, relocation and narrow/200-percent text layout. Browser results and
agent review do not qualify screen readers or intended-user usability.

The first development wheel exposed missing installed Git provenance; the fixed
SDK context now supplies the verified descriptor identity without changing
historical M3 source bytes. Another development probe incorrectly assumed sorted
JSON keys; it was corrected to require native M3's exact serialization. Those
failed probes are retained locally under ignored `results/m3-integration/` and
temporary test logs. The first browser invocation failed before test execution
because the macOS sandbox denied Chromium's Mach-port registration; an explicit
process-authorized invocation supplies the actual browser evidence.

## One GluPredKit mapping assessed

A source inspection pinned
[GluPredKit revision 12c7011](https://github.com/replicahealth/GluPredKit/tree/12c70117c48eca54e920a0af69746949922407c1)
without installation or execution. Its
[Ridge implementation](https://github.com/replicahealth/GluPredKit/blob/12c70117c48eca54e920a0af69746949922407c1/glupredkit/models/ridge.py)
selects stored feature columns and a subject-associated fitted model. A proposed
portable export would select the frozen 30-minute output and preserve all
coefficients, intercepts, feature order and preprocessing state. It is not the
existing OpenT1D Ridge donor and has not been numerically qualified here.

The [feature builder](https://github.com/replicahealth/GluPredKit/blob/12c70117c48eca54e920a0af69746949922407c1/glupredkit/helpers/scikit_learn.py)
uses row shifts for lagged columns and negative shifts for optional future
features. Only exact CGM history at 0/−5/−10/−15/−20/−25 minutes can map;
row adjacency alone cannot establish M3 availability or clock-segment validity.
The [base predictor](https://github.com/replicahealth/GluPredKit/blob/12c70117c48eca54e920a0af69746949922407c1/glupredkit/models/base_model.py)
returns a trajectory rather than M3's single scalar. Selecting its sixth
five-minute output requires explicit output-order verification. Additional
subject IDs, imputation, future covariates or unsupported model state cannot be
silently added to the historical-CGM-only callback. A future adapter needs a
separately identified environment/export contract, development-only fitting,
rights review and direct/exported numerical parity before admission. No general
GluPredKit compatibility or new dependency is claimed.
