# 0089 — A bounded internal candidate and comparison reader transition

Date: 31 October 2026. Status: implemented; selected before implementation and qualification.

## Decision

Implement roadmap step 6 first for the two standard-library MMTT tasks, their
derived plans and frozen comparisons. Build a clean, noneditable installed
wheel/workbench candidate on the selected Apple Silicon macOS CPython 3.12 host.
Its descriptor admits exactly those two tasks. This is an internal application
candidate requiring the declared host interpreter, not a bundled Mac installer
or public release. Keep the existing broader developer-wheel default separate.

The actual predecessor A is merged PR 43, source
`fc041c6e51463ae640d97c55719e742253e453e0`. Retain its clean wheel, receipt,
native task chains, frozen comparisons and reports before changing the reader.
B has a different source revision and changed comparison validation/identity.
The supported transition is a current, trusted comparison reader that validates
every original definition field, while explicitly admitting one exact older
comparison reader identity for the two selected tasks. A packaged registry pins
the complete A reader and complete qualified B reader source closure, roots and
schema. Bind the registry bytes in B's reader identity and installed manifest.
An arbitrary old or altered current reader is not an admitted transition.

Original scientific plans, input bytes, native readers, numerical methods,
protocols, units, allocation, uncertainty, first-attempt policy, failures and
tolerances stay bound exactly as before. Preserve A's original definition in
report bytes; report the actual B reader/transition separately in the operation
receipt. Reconstruction uses a read-only project lease and cannot append a
verification event. No project migration, archived-code execution, downloaded
reader or automatic trust of an application label is introduced.

The native M4 declared source inventory transitively includes the changed shared
services. Its old projects and connected studies are outside this compatibility
pair; refuse them without altering evidence. A new native-capable artifact needs
its own runtime attachment and relevant native qualification. The smaller
candidate must enforce its two-task capability boundary rather than merely hide
native buttons. Signing, notarisation, clean-host installation, other platforms,
independent use and public release remain separate gates.

## Preselected acceptance

Retain complete, incomplete, failed, interrupted, unattempted and later-retried
MMTT evidence. A freezes comparisons before execution and saves explicit ledger
tips; B reconstructs their reports byte for byte after A is unavailable and the
whole project has moved. Check Python, CLI and authenticated workbench download,
startup, cancellation, quit/relaunch, new B work and rollback to A. Hash the
entire original project before and after each read/refusal. Repeat independent
constant-input/reference and sampling controls, retaining missing values and
development/evaluation separation. Candidate-bound formative materials remain
unanswered; no participant or recipient is presumed.

Counterexamples include the previous strict reader refusing the changed identity,
altered/resealed A reader metadata or non-reader definition fields, changed B
renderer/helper/task source even with an updated wheel manifest, unknown schema,
mixed native projects and native execution through both facade and bootstrap.
Do not treat an import error or timeout as detection. Keep failed rehearsals and
their cause distinct from the final clean candidate qualification.

One owner implements shared contracts and runs the final full repository check.
A separate read-only technical reviewer challenges the actual diff and negative
controls; that review is not independent scientific or human validation.
